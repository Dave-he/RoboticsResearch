## 当前在用的方案:systemd user timer (2026-07-01 起)

参考 LNN 项目的 `lnn-daily-research.{timer,service}` 改写。

### 组件

- **入口脚本**:`scripts/run_daily_robotics_task.sh`(本仓库)
  - 调 `python3 scripts/daily_robotics_research.py ...`
  - 若有变更则 `git add docs papers analysis` + `git commit` + `git push`
- **systemd service**:`~/.config/systemd/user/robotics-daily-research.service`
  - `Type=oneshot`,`WorkingDirectory=/mnt/ssd/codespace/research/RoboticsResearch`
  - 通过 environment 注入 `MAX_ARXIV=80`、`COMMIT_AND_PUSH=1` 等参数
- **systemd timer**:`~/.config/systemd/user/robotics-daily-research.timer`
  - `OnCalendar=*-*-* 07:00:00`(故意比 LNN 的 06:30 错开 30 分钟,避免同时打 arXiv)
  - `RandomizedDelaySec=10m`
  - `Persistent=true`(机器关机后下次开机自动补跑错过的任务)

### 安装命令

```bash
# 1. 让入口脚本可执行
chmod +x /mnt/ssd/codespace/research/RoboticsResearch/scripts/run_daily_robotics_task.sh

# 2. systemd 重载 + 启用 timer(已在本机执行)
systemctl --user daemon-reload
systemctl --user enable --now robotics-daily-research.timer

# 3. 查看下次触发时间
systemctl --user list-timers | grep robotics

# 4. 立即试跑一次(可选)
systemctl --user start robotics-daily-research.service
journalctl --user -u robotics-daily-research.service -n 50
```

### 行为约定

- 每天 07:00 CST(±10 min 抖动)自动跑,失败无回滚,下次会覆盖
- 提交信息为 `chore(daily): update RoboticsResearch digest <YYYY-MM-DD>`
- 只覆盖 fetch 部分(`papers/daily/` + `docs/daily/` + `analysis/repo_watchlist/` + 全局索引),**深度研读报告**仍由人工 / interactive session 触发(通过 `/goal` 进入日研究流程时一并产出)
- 每次运行结束前会额外跑两件事:**重建索引主表**(`build_report_index.py`)与**周期产物门禁**(`check_periodic_artifacts.py`)。门禁失败**不中断**当天抓取,只在 `logs/daily_cron.log` 留告警

### ⚠️ GitHub Search API 配额(2026-10-20 定位)

未认证的 GitHub **Search** API 限额是 **10 次/分钟**,而抓取脚本每个 query 发一次请求、共 8 个 query —— **几乎打满一个配额窗口**。

**症状**:某些日期的 `papers/daily/*.json` 里 `repos` 只有 47–58 条(正常是 91–93)。这**不是**「当天机器人仓库变少了」,而是**尾部几个 query 被限流后返回空**。

**为什么难发现**:旧代码把异常吞掉了(`except Exception: continue`),JSON 里也没有任何错误字段 —— **产物看起来完全正常,只是少了一半数据**。

**已落地的处理**:

| 措施 | 说明 |
|---|---|
| 配额感知 | 读取响应头 `x-ratelimit-remaining` / `x-ratelimit-reset`,剩余 ≤2 时主动等到窗口重置 |
| 失败重试 | 命中 403 限流时等待 reset 后重试一次 |
| **诊断落盘** | 每日 JSON 新增 `diagnostics` 字段,记录失败 query 数与原因 |
| **digest 显式告警** | 抓取不完整时,digest 顶部会出现「⚠️ 本次抓取不完整」段落 |

**根治建议**:配置 `GITHUB_TOKEN` 环境变量(令牌已有读权限即可),限额从 10 次/分提升到 **30 次/分**,8 个 query 可一次跑完,不再有窗口边界问题。
设置后 GitHub Actions 侧已默认注入 `secrets.GITHUB_TOKEN`;systemd 侧需要在 unit 的 `Environment=` 中配置。

**历史证据**:`logs/daily_cron.log` 中有 13 次 `[warn] GitHub query failed ... HTTP Error 403: rate limit exceeded`(2026-07-14 ~ 2026-09-28 期间共 77 次运行中 7 次触发),失败的一定是 query 列表的尾部。

## 周期产物门禁(2026-10-20 新增)

`scripts/check_periodic_artifacts.py` 把协议 §7 从「描述」变成「可检查」:

```bash
python3 scripts/check_periodic_artifacts.py          # 人类可读报告
python3 scripts/check_periodic_artifacts.py --json   # 机器可读
python3 scripts/check_periodic_artifacts.py --check  # 安静,只返回退出码
```

**检查项**:每日抓取连续性 · 周报存在性 · 月度合成存在性 · 零产出周/月 · 部分抓取 · 重复研读报告。

**基线**在 `configs/periodic_gate.yaml`:本项目 2026-06-07 ~ 2026-09-27 是骨架期(抓取不连续、无周报节奏),因此门禁只从 2026-07-01(每日)/ 2026-W40(周报)/ 2026-07(月度)起算。已复盘归档的历史断档登记在 `acknowledged_stalls` 中,不会重复告警。

**CI**:`.github/workflows/periodic-artifacts-gate.yml` 每天 09:10 CST 跑一次,失败会在 Actions 里标红。**它是独立工作流,不会阻断每日 digest** —— 缺一篇周报不该让明天的抓取停摆。
