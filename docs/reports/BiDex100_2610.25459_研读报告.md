## 核心问题

### 既有评测的空白在哪(论文 §I / §II 的自述)

论文对现状的判断是**分三层递进的**,而非笼统的「任务不够多」:

1. **主流基准把灵巧维度整个抽掉了。** Meta-World、RLBench、LIBERO、CALVIN、RoboCasa、ManiSkill 全部是**单臂 + 平行夹爪**,「灵巧」这个变量在评测里根本不存在。Table I 的 DoF 列对这一整排基准全为「–」。
2. **灵巧手基准换来了「窄」,丢掉了「真」。** Bi-DexHands、DexMV 这类是**从零 RL / 人类视频重定向**的小任务集,**没有语言 grounding、没有大规模演示、没有自动化组合式打分**。
3. **新近的大规模双手基准仍然是夹爪 + 二值分数。** RoboTwin / RoboTwin 2.0、RoboDojo 确实做到了双手与统一协议,但**依然不考多指灵巧**,且「scoring remains predominantly binary」。DexJoCo 是最接近的先行者(双手灵巧 + 遥操作演示 + 匹配 ID/OOD),**但只有 11 个任务、且仍是二值打分**。

### 论文认为的根因

论文的根因判断不在「能力不足」,而在**评测分辨率**。它明确写道:随着 VLA 训练语料膨胀,窄范围 pick-and-place 套件上的**平均成功率已经饱和**,基准的区分力因此从「任务覆盖度」迁移到**能力边缘(capability edges)** ——记忆场景状态、维持长时程、遵守中途切换的指令、少样本学习、以及在视觉/几何偏移下优雅退化。**58-DoF 双手灵巧系统会把这些边缘全部放大**,因为动作空间高维冗余、成功取决于接触密集的指间协调,而**二值成功率看不见这些失败模式**。

> 换言之:根因不是「机器人不会做」,而是 **「我们用的尺子测不出机器人哪里不会做」**。这是从「评测任务」升维到「评测能力」的关键判断。

### 提出的新视角

**用「能力画像(capability profile)」取代「单一排名」。** 具体三件事:

1. **按所考察的能力组织任务**,而不是按场景或物体类型组织 —— 于是排行榜位置**可分解**为可解释的向量;
2. **进展分数(progress score)取代二值成功** —— 部分完成与彻底失败必须可区分;
3. **匹配的 ID/OOD 对照** —— 域内表现与鲁棒性直接可比,而非各论文各自定义协议。

论文明确把「**可复现与可比的分数**」列为三条设计原则之一:机器可检的谓词合取、确定性种子评测、基于进展的子任务信用,**以取代人工评分与逐论文自定协议**。

> 📌 **本报告的判断:这是 2026 年至今少见的「把评测工具而非新方法作为主贡献」的论文形态,且这个选择是对的。** 参照本项目 §12.3「变量控制」维度,本文在**同接口、同数据混合、同种子**下横评 7 个 VLA,控制变量质量属于本项目已收录论文中的**上档**。

## 方法论与核心思路

### 1. 任务空间:106 个任务是怎么来的,以及分类体系

任务不是「攒」出来的,而是**先定能力轴、再填任务**。论文三条设计原则之一是「**Diagnose capabilities, not tasks**」—— 任务按其所考察的能力组织,而不是按场景或物体类型。

| 能力轴 | 任务数 | 考察什么 | 关键设计 |
|---|---:|---|---|
| **Generalization** | 40 | 视觉与几何泛化、跨本体迁移 | 单/少阶段技能:lifting、placement、insertion、threading、cooking;**10 个 `kitchen_*` 任务跑在 Astribot S1 上,其余 30 跑在 dual Franka 上** |
| **Instruction-Following** | 20 | 指令保真度 | 三种测法:**count**(同场景不同数量,如浇 1 株 vs 2 株植物、每手锤 1 根 vs 2 根钉)、**combo**(两条指令合取)、**switch**(回合中途换指令,策略须服从**当前**命令而非记忆中的) |
| **Limited-Demonstrations** | 26 | 少样本技能习得 | **每任务仅 30 条演示**(其余轴为 100 条);含 10 个铰接机构任务(微波炉、收银机、电饭煲),需要铰接/滑动/旋转关节的**力感知驱动** |
| **Long-Horizon** | 10 | 时程深度 | 4–9 个子任务,平均 6.5 个物体/场景,演示均长 **48.3 s**;BBQ 烧烤、冰箱补货、甜点摆盘、回收分拣 |
| **Memory** | 10 | 潜在状态追踪 | **知觉混淆**下的状态记忆:color-swap 杯(按按钮序列后立方体颜色被抹除,须回忆后选对杯)、picnic-basket FIFO(取出顺序须等于放入顺序)、memory cups(揭示阶段后目标被隐藏) |

📌 **本报告独立核验(从发布的 212 个 YAML 逐条解析)**:各轴任务数、每任务子任务数、演示条数、谓词类型与实例数,**与论文陈述逐项吻合**(470 谓词实例、42 类型、106 任务、8,080 演示全部对上)。**这是本报告对该论文可信度的第一道实测背书。**

### 2. 状态描述与成功判定:从「场景」到「声明式规范」

每个任务是一份**声明式规范**(Eq. 1):

$$
\mathcal{T} = \big(\mathcal{R},\ \mathcal{O},\ \mathcal{A},\ \mathcal{G},\ \mathcal{L}\big)
$$

- $\mathcal{R}$ 命名放置区域,每个含中心、xy 范围、yaw 范围 —— **重置时物体位姿从区域内均匀采样,因此同一 seed 族内不同 episode 的初始条件也不同**;
- $\mathcal{O}$ 可动物体、$\mathcal{A}$ 铰接初始状态、$\mathcal{L}$ 语言(可含回合中途切换的指令日程)。

目标是 $K$ 个子任务的合取(Eq. 2):

$$
\mathcal{G} = \bigwedge_{k=1}^{K} S_k, \qquad S_k = \bigwedge_{p \in \mathcal{P}_k} \phi_p(\mathbf{s}_t)
$$

每个 $\phi_p$ 取自**带类型、带阈值参数的谓词库**,覆盖几何类(containment / support / pose)、事件与记忆类(计数与状态回忆)、以及**否定类**(police 禁止结果)。仓库中实际谓词类型分布:`lifted` 119 次、`inside_contact` 58、`not_inside` 26、`open` 23、`supported_in_region` 23、`inside` 21、`not_lifted` 19…… 与论文 Fig. 8(d)「14 个最常用谓词」的说法一致。

**成功判定是本设计最扎实的部分**,论文用三套机制硬化 latching 语义(§III-C):

1. **must-hold 谓词**:除被 latch 外,episode 结束时仍须为真 → 击穿「碰一下就走」的 touch-and-go;
2. **latch-violation 谓词**:一旦出现禁止状态,永久作废该子任务(如浇错植物);
3. **ordered subtasks**:后续信用被前置完成所 gate。

📌 **本报告实测**:417 个子任务中 **213 个(51.1%)带 must-hold**,**28 个 latch-violation 谓词实例**,**71 处 order_group**;13 个零权重子任务(占 3.1%)全部是**否定式安全约束**(如「另一把餐具不得被拿起」「橙色须仍留在桌上」)—— 与论文「零权重安全或终止约束仍参与 strict success」的说明一致。**79/106 任务(75%)的最后一个子任务带 must-hold**,这是「末态必须成立」的终端门。**这套机制的工程实现是真实的,不是纸面设计。**

### 3. 双手本体与资产

- **dual Franka**:**2 × 7-DoF Franka Research 3 臂**,共基座,每臂装 **22-DoF 灵巧手**,共 **58-DoF**;执行 106 个任务中的 **96 个**;
- **Astribot S1** 人形本体,同样两只 22-DoF 手 + 两条 7-DoF 臂,执行 **10 个 Generalization 任务**;
- 📌 **本报告核验**:仓库 106 个 base YAML 的 `robot_type` 字段实测为 **96 × `dual_fr3v2_sharpa` + 10 × `astribot_s1_fixed_sharpa`**,与论文 §III-B 逐字一致;灵巧手资产目录实测为 `bidex/robots/hands/sharpa_wave/`,即 **Sharpa Wave 22-DoF 灵巧手**(参考文献 [29] 指向 sharpa.com)✅;
- **资产**:266 个唯一可见资产、9 个语义类别,来源含 RoboCasa-Objaverse、Lightwheel、HOPE、扫描件、Turbosquid、Articraft 及自建装配/控制原语;每个资产都模拟了**网格、质量与摩擦**。**刚性 + 铰接两类齐全,但完全没有柔性物体** —— 论文自述「rigid-body benchmark」。

> ⚠️ **一处需要记录的实物口径出入**:项目页写「**Shadow-style** 22-DoF 灵巧手」,而论文参考文献 [29] 与仓库资产目录均指向 **Sharpa Wave**。**论文与代码一致,项目页描述不准。** 引用时应以 Sharpa Wave 为准。

### 4. 观测与动作空间

- **观测**:头/左腕/右腕 **3 路 RGB-D,480×360 @ 25 Hz**(6 个视频流)+ 完整本体感知(臂/手关节位置与速度、绝对末端位姿),合计 **130 维**;
- **动作**:**58 维关节位置目标** $\mathbf{u}_t = [\mathbf{q}^{\mathrm{arm}}_{\mathrm{tgt}}, \mathbf{q}^{\mathrm{hand}}_{\mathrm{tgt}}]$,位置控制执行器;另提供 EEF 控制模式(经 IK 转关节目标),仓库实现了 `joint` / `robot_ee` / `camera_ee` 三种 58-D 表示;
- **双手协调如何参数化**:**不额外引入协调变量** —— 协调由**共享的 58 维关节空间 + 任务谓词**隐式承载。这是关键设计取舍:接口保持统一,协调的难度完全体现在任务本身(如「左手开盖 → 左手放鼓槌 → 右手放鱼 → 右手放南瓜 → 左手合盖」的**链式左右手交替**)。

📌 **论文提供的协调性证据是描述性的,而非消融性的**:Fig. 2(a) 显示两手末端执行器工作空间「partition but substantially overlap」(分区但大幅重叠,迫使双手协调);Fig. 2(b) 显示 44 个手关节**全部 5 指均有显著运动**,拇指 CMC 与手指 MCP 关节行程最大;Fig. 4 显示双手 44-DoF 姿态落在低维流形上 —— **8 个主成分即解释 80% 姿态方差**,k-means(k=5) 聚类从张开手掌连续过渡到握拳。**⚠️ 这是「高维手仍可被紧凑协同基描述」的证据,但不是「双手比单手更好」的证据 —— 论文从未做单手对照实验(见「局限」)。**

### 5. 评测协议

| 维度 | 规定 |
|---|---|
| 试次 | 每 (模型, 任务, 域) = **2 seed × 25 episode = 50 次**;每任务 ID 50 + OOD 50 = **100 次**;每模型合计 **10,600 次** |
| 种子 | **ID = seed 0/1,OOD = seed 2/3**;物体位姿由 (任务, seed, episode) 确定性导出 |
| 超时 | 任务显式 `max_steps` 优先;否则 **1.2 × 演示长度 P90**,无演示数据时 30 s 兜底;**超时保留已 latch 的部分分数** |
| 成功判定 | **strict success = ∏ e_k(T)**,需全部子任务成立;progress score ∈ [0,100] |
| 统计口径 | 每域每轴报「mean strict success / mean progress score」;**Overall = 全部 212 个 task-domain 均值的等权平均** |
| OOD 终止 | 抓住 distractor **立即以当前分数终止 episode** → OOD 同时惩罚「分心」与「误抓」 |
| 人工干预 | **零**。逐任务分解与完整 rollout 视频留存备查,leaderboard 无需人工标注 |

> 📌 **本报告独立验算了 Overall 的定义**:Table III 的 Overall 列**不是**五个轴的简单平均,而是**按各轴任务数(40/20/26/10/10)加权的均值**。验算:LingBot = (61.35×40 + 35.90×20 + 66.15×26 + 38.20×10 + 26.00×10)/106 = **52.21**,与论文报告值**完全一致**;7 个模型全部对上(π0.5 = 50.40 ✅,GR00T = 42.32 ✅,OpenDM = 23.06 ✅,Galaxea = 21.68 ✅,Xiaomi = 4.40 ✅,InternVLA = 1.51 ✅)。**口径可核、无隐藏加权。**

## 核心公式提取

### 公式 1:任务规范与目标合取(§III-C, Eq. 1–2)

$$
\mathcal{T} = \big(\mathcal{R}, \mathcal{O}, \mathcal{A}, \mathcal{G}, \mathcal{L}\big), \qquad
\mathcal{G} = \bigwedge_{k=1}^{K} S_k, \qquad S_k = \bigwedge_{p \in \mathcal{P}_k} \phi_p(\mathbf{s}_t)
$$

**符号解释**:
- $\mathcal{R}$ 放置区域集合;$\mathcal{O}$ 可动物体;$\mathcal{A}$ 铰接初始状态;$\mathcal{L}$ 语言(可含指令日程)
- $S_k$ 第 $k$ 个子任务;$K$ 子任务数(1–10,均值 3.9);$\mathcal{P}_k$ 该子任务的谓词集;$\phi_p(\mathbf{s}_t)$ 类型化、带阈值的谓词函数

**意义**:把「场景」抽象成**可机检的谓词合取**,这是整个基准可自动化、可跨论文比较的技术底座。

### 公式 2:latching 语义与有效完成态(§III-C, Eq. 3 核心)

$$
\ell_k(t) = \max_{\tau \le t} c_k(\tau), \qquad
e_k(T) = \ell_k(T)\,(1 - m_k + m_k h_k(T))\,(1 - v_k(T))
$$

**符号解释**:
- $c_k(t)$ 子任务 $k$ 的**瞬时**真值;$\ell_k(t)$ **latched 状态**(单调不减,进度不可被后续扰动撤销)
- $m_k \in \{0,1\}$ 该子任务是否含 must-hold 谓词;$h_k(T)$ 末态真值;$v_k(T)$ 是否发生过 latch-violation
- $e_k(T) \in \{0,1\}$ **有效完成态**

**意义**:三个因子分别封死三种投机路径 —— $\ell_k$ 封「完成后破坏仍得分」,$m_k h_k$ 封「碰一下就走」,$(1-v_k)$ 封「干了禁止的事仍得分」。

### 公式 3:严格成功与进展分数(§III-C, Eq. 3)

$$
\text{success} = \prod_{k=1}^{K} e_k(T), \qquad
\text{score} = \sum_{k=1}^{K} w_k\, e_k(T), \qquad w_k \ge 0,\ \sum_k w_k = 100
$$

**符号解释**:
- $w_k$ 子任务整数权重(每任务和为 100);$K$ 子任务数
- success 为**严格合取**(全对才算成功);score ∈ [0,100] 给出部分信用

**意义**:**用同一套 latch 状态同时导出「二值严格」与「连续进展」两个指标** —— 这是本论文最重要的工程选择。

### 公式 4:OOD 缩放因子的确定性采样(§IX / §III-E)

$$
f_{\text{ep}} \sim \mathcal{D}\big(f_{\text{anchor}} \pm 0.18\big), \quad
f_{\text{anchor}} \in \{0.85, 0.9, 1.1, 1.15\}
$$

并按 regime 裁剪到 $[0.65, 0.96]$(变小)或 $[1.04, 1.35]$(变大)。

**意义**:把「物体大小偏移」从随机漂移变成**可复现的分级变量**,从而 OOD 分数可跨机器、跨模型重放。

### 2. 五条可以下判断的结论

**① ID 排名与 OOD 排名显著错位 —— 这是本论文最被低估的发现。**

| LingBot-VLA-v2 | **1** | 3 | 52.21 | 1.68 | 3.2% |
| π0.5 | 2 | 2 | 50.40 | 3.30 | 6.5% |
| **GR00T-N1.7** | **3** | **1** | 42.32 | **5.45** | **12.9%** |
| OpenDM-DM05 | 4 | 4 | 23.06 | 1.47 | 6.4% |
| Galaxea G0.5 | 5 | 5 | 21.68 | 0.77 | 3.6% |
| Xiaomi XR1 | 6 | 7 | 4.40 | 0.02 | 0.5% |
| InternVLA-A1.5 | 7 | 6 | 1.51 | 0.32 | 21.2% |

**域内第 1 名(LingBot)在域外掉到第 3;域内第 3 名(GR00T)在域外登顶,且保持率 12.9% 是 LingBot 的 4 倍。** 这直接说明:**只看域内榜单选型,会选出一个域外几乎不可用的策略。** 对产业而言这是本篇最有决策价值的一条 —— 采购/选型不能只看 ID 分数。

**② OOD 性能整体崩塌到近零 —— 幅度本身才是结论。**

从 ID 到 OOD,7 个模型的 Overall 成功率**全部下降 7.8×–220×**,最高者 GR00T 也只有 5.45%。按轴看,OOD 成功率在 40 个 Generalization 任务上意味着 **93/2000 次成功**(GR00T 最好),Memory 轴最好也只有 **19/500**;**Long-Horizon 轴上 7 个模型有 4 个是 0/500**。⚠️ 这说明当前 VLA 在双手灵巧场景下的**域外鲁棒性基本不存在** —— 比「慢」严重得多,是「不成立」。

**③ 进展分数确实揭示了二值成功掩盖的「接近完成」。**

论文明确指出:ID Long-Horizon 上**每个模型的严格成功率都低于其进展分数** —— 最高成功率 **38.20%**,最高进展分数 **66.78%**。本报告逐行核验 7 个模型,Long-Horizon 轴**全部满足 SR < Score**(3.20/17.45、32.80/62.32 等)。**这意味着约 3/4 的长时程任务「做对了大部分但没做完」,二值分数把这部分能力完全抹掉。** 这是 §III 诊断性主张最硬的证据。

**④ 能力轴之间的排序不一致,证明「单一排名」确实不够。**

各轴 ID 最优模型:Generalization = LingBot(61.35)、Instruction-Foll. = π0.5(36.60)、Limited-Demo. = π0.5(66.23)、Long-Horizon = LingBot(38.20)、Memory = π0.5(33.00)。**OOD 侧则几乎被 GR00T 垄断 4/5 轴**(Gen 4.65、Inst 3.10、LD 10.23、LH 2.60)。**没有任何一个模型在所有轴上领先** —— 能力画像的必要性由此得到实证支持,而非仅是设计口号。

**⑤ Memory 轴是全场最难的轴(除 OOD 外)。**

ID Memory 最高仅 33.00%(π0.5),Long-Horizon 最高 38.20%。**而 Memory 是唯一一个「单帧不可解」的轴**(颜色被抹除、取出顺序须等于放入顺序、揭示后隐藏)。**这 33% 的上限说明:当前 VLA 的隐式状态追踪能力,在真正需要它时是失效的。** 对本项目关注的「具身智能长期状态保持」是负面但重要的信号。

### 3. 本报告读出来的额外发现(论文未展开)

**📌 发现 A:「Limited-Demonstrations 隔离了 30 样本习得」这个主张不成立 —— 该轴同时是「最简单的轴」。**

论文明言「Limited-Demonstrations isolates acquisition from 30 examples」。但本报告实测 YAML 结构发现:

| 能力轴 | 任务数 | 演示数 | **平均子任务数 K** | K=1 的任务数 | ID Overall(SR) |
|---|---:|---:|---:|---:|---:|
| Generalization | 40 | 100 | 3.80 | 4 | 24.90–61.35 |
| **Limited-Demos** | 26 | **30** | **3.23** | **12** | **35.69–66.23** |
| Instruction-Foll. | 20 | 100/30 | 4.00 | — | 1.80–36.60 |
| Long-Horizon | 10 | 100 | 6.50 | 0 | 3.20–38.20 |
| Memory | 10 | 100 | 3.60 | 0 | 0.00–33.00 |

**7 个模型中有 7 个在 Limited-Demos(30 条演示)上的 ID 成功率高于 Generalization(100 条演示)** —— LingBot 66.15 > 61.35、π0.5 66.23 > 55.45、GR00T 61.38 > 46.55、OpenDM 35.69 > 33.05、Galaxea 39.62 > 24.90、Xiaomi 7.15 > 6.40、InternVLA 4.23 > 0.80。

> **换言之:这个轴测到的不是「少样本习得能力」,而是「少样本 + 任务本身更容易」的混合量。** 因为 LD 轴 26 个任务里有 **12 个是 K=1 的单步任务**(铰接机构开合,如开微波炉/开收银机/开瓶盖),而 Generalization 轴 40 个任务中 K=1 的只有 4 个、且多步任务占比更高。**「数据量」与「任务难度」两个变量在轴内完全混淆。** 要真正隔离数据效率,需要在**同一批任务**上做 30/100/400 三档的对照,本基准**没有提供**这个对照。

**📌 发现 B:「matched ID/OOD」在机器人初始位姿上并不 matched。**

论文 §XII 明确写:*「ID protocol additionally restores a deterministically selected working robot pose, while OOD uses the default robot reset pose.」* 本报告在代码中定位到该实现(`bidex/eval/run_leaderboard_eval.py` 的 `restore_state_from_collection` 与 `load_collection_init_states`):ID 从 H5 中恢复**录制的机器人工作位姿**(仅恢复臂+手的 58 维关节位置),OOD 则 `init_states = np.zeros((0,0))` —— **完全从默认复位位姿起步**。

> **后果:ID 域起点是「已知可行的姿态」,OOD 域起点是「默认姿态」。** 因此 OOD 的性能下降里,**混入了「初始位姿更差」这一项,而非纯粹的「视觉/空间偏移鲁棒性」。** 这解释了为什么 OOD 崩塌如此剧烈(保持率仅 0.5%–12.9%)。**这不是造假 —— 论文在附录里诚实地写出来了 —— 但主文 §III-E 把 OOD 描述为「controlled visual and spatial changes」时,读者极易误以为两域起点一致。** 📌 **这是本报告认为本篇最需要打折的一处口径**:OOD 分数应读作「**域外 + 起始位姿变更**的联合退化」,不能直接读作「视觉鲁棒性」。

**📌 发现 C:「双手灵巧」这一核心主张,从未与单手或夹爪做过对照。**

论文的三条设计原则第一条是「Dexterity is the object of study」,并称任务「require dexterous hands for skills beyond conventional grippers, such as hammering nails and watering」。但:

- 全文**没有任何单手 / 夹爪基线**;
- 仓库 eval harness **其实支持** `--arm single_arm`(`run_leaderboard_eval.py` 的 argparse choices 为 `dual/left/right/single_arm`,含 per-task 路由),**但论文未使用、未报告**;
- 因此「这些任务确实需要灵巧手」是**设计断言,不是实验结论**。Fig. 4(b) 的 PCA 结论(8 主成分解释 80% 姿态方差,双手 44-DoF 与单手 22-DoF 对比)是**描述手部运动的内在维度**,**不是「单手做不到」的性能证据**。

> 📌 **对产业的直接含义:不能引用本文来论证「必须买灵巧手」—— 本文没有做这个对照。** 这是一个**已具备工具但未执行**的实验,建议作为社区跟进项。

**📌 发现 D:「取放」类子任务几乎不受 must-hold 保护,latch 语义留下了一条「碰一下就走」的缝。**

本报告实测:**104 个以 pick up / lift / grasp 命名的子任务中,99 个(95%)不带 must-hold**。由于 $\ell_k$ 单调、且多数「取起 X」子任务无末态约束,**一个策略只要在某一瞬间把物体抬过阈值即可锁定该子任务信用,随后放下也不算失败**。论文的 must-hold 机制被重点用在了**放置/保持类**子任务上(79/106 任务的最后一个子任务带 must-hold),**但对「取起」这一半的中间步骤没有终端门**。

> 这不是「刷分漏洞」的严重漏洞 —— 因为放错位置会被后续 must-hold 子任务判负,总 success 仍是合取。但它意味着 **progress score 可以在物体并未被真正稳住的情况下拿到相当份额**,**score 与 success 的差距在含多次取放的复合任务上会被系统性放大**。论文用 progress score 做「部分完成」诊断时,这个偏差未被讨论。

**📌 发现 E:零权重子任务与 latch-violation 的实际分布,比论文描述更稀疏。**

13 个零权重子任务全部是否定式安全约束(「另一把餐具不得被拿起」「橙色须仍在桌上」「三个立方体须全被盖住」),分布在 8 个任务里。其中 **7 个既无 must-hold 也无 latch-violation**,属于**纯声明式否定约束**。这类约束是纯逻辑判定(而非物理接触判定),**理论上存在被状态脚本绕过、只满足语义而不产生真实物理后果的空间**。不过由于它们零权重、不影响 progress score,只影响 strict success,**属于低风险但值得记录的「语义 vs 物理」缝隙**。

## 局限性与未来展望

### 论文自述的局限(§XIV 原文要点)

1. **刚体基准**:MuJoCo 不建模流体、柔性物体,也不具备硬件级的高保真摩擦接触;
2. **sim-to-real 未验证** —— 在这些演示上训练的策略向物理平台的迁移**仍待验证**;
3. **物体库以桌面食物与厨房场景为主**(though diverse);
4. **OOD 偏移是脚本化且有限的**,学习式或对抗式生成的偏移分布是自然的扩展方向。

### 本报告在阅读中发现的额外问题

1. 🔴 **OOD 的初始位姿不对称(见「发现 B」)。** 这是本篇最需要打折的一处:**OOD 分数不是纯「视觉/空间鲁棒性」**。主文 §III-E 的表述「controlled visual and spatial changes」会让读者严重高估其含义。**建议社区在引用 OOD 数字时一并标注此前提。**
2. 🔴 **Limited-Demos 轴的难度混淆(见「发现 A」)。** 「30 样本习得」与「任务更简单」在轴内完全混淆,**7/7 模型的该轴分数高于 100 样本轴**。**该轴当前不能用于数据效率结论。**
3. 🔴 **无单手 / 夹爪基线(见「发现 C」)。** 论文的第一设计原则「灵巧是被研究对象」在实验上未被验证;harness 已支持 `single_arm` 却未跑。**这是一条零边际成本的补做路径。**
4. 🟠 **模型对比非等条件。** 动作头从 32/27/55-DoF 迁到 58-DoF 的方式各异(重初始化 vs 部分复制+零填充),**信息保留量级不同**;训练步数 60k–400k(6.7× 跨度);π0.5 用 delta 动作而其余用 absolute;π0.5/Galaxea 推理去噪步数(10 / 单步)与 GR00T(4 步)也不同。**「哪個模型更强」在本表内不是一个被严格控制的问题。**
5. 🟠 **OOD 分数的统计力极弱。** Long-Horizon OOD 上 4 个模型是 **0/500**,Memory OOD 最好 **19/500**。**在这些格子上,模型间 1–2 个百分点的差异完全落在噪声内**,但表格以两位小数呈现,容易被过度解读。论文未给置信区间或多种子方差。
6. 🟠 **「双手协调」未被真正度量。** 双臂交替任务(如 `grill_drumsticks_fish_and_squash` 的左-左-左-右-右-右-左链条)在语义上要求协调,但**没有任何指标区分「真正双手协同」与「两只手各自最优」** —— score 只看终态谓词是否满足,不惩罚分工方式。**这正是任务书所问的那一类问题,答案是:本篇没有回答。**
7. 🟡 **progress score 在含多次取放的任务上系统性偏高(见「发现 D」)。** 95% 的「取起」子任务无终端门,latch 单调性允许瞬时满足即锁信用。**score 与 success 的差距因此被放大。**
8. 🟡 **无柔性物体、无流体、无真机。** 论文自述已覆盖前两项;**「零真机」使得整套 8,080 条演示的 sim-to-real 价值完全未知** —— 演示采集在仿真中用 FACTR 外骨骼手套 + Apple Vision Pro 完成,**这套遥操作栈本身没有在真机上验证过采集质量**。
9. 🟡 **Table VI 缺失。** 全文表编号从 TABLE V 直接跳到 TABLE VII(VII = 观测/动作模态,VIII = 任务规范与计分语义,V = 谓词目录)。**疑为排版遗漏,非本报告推测的隐含内容。**
10. 🟡 **项目页与论文口径不一致。** 项目页写「five scripted out-of-domain shifts」(论文为**六**族)、distractor「2–6 sibling objects」(论文与 YAML 均为 **3–9**)、手为「Shadow-style」(论文与仓库均为 **Sharpa Wave**)、资产「~300 meshes」(论文为 **266**)、且称「All 106 tasks are evaluated on the dual-Franka platform」(论文为 **96**)。**论文正文与代码一致,项目页是唯一不可靠来源 —— 引用时以论文 + 仓库为准。**

### 未来方向(论文提的 + 本报告推断)

**论文方向**:推广到更多形态与物理现象(流体、柔性)、学习式/对抗式 OOD 偏移生成、在物理平台上验证 sim-to-real。

**本报告推断(按优先级)**:

1. **补做同任务跨数据量对照**(30/100/400 三档),把 Limited-Demos 轴的难度混淆拆开 —— **这是让该轴真正成立的最小改动**;
2. **补做单手 / 夹爪基线** —— harness 已就绪,零边际成本,可直接回答「灵巧是否必要」;
3. **统一 ID/OOD 初始位姿**(或把位姿变化作为独立一维报告),使 OOD 分数可解释为纯粹的偏移鲁棒性;
4. **引入「协调度」指标**(如双手同时活跃度、跨手任务交接时刻的对齐误差),把「协调」从语义要求变成可测量量;
5. **给 OOD 低分格加置信区间**,或对 OOD 采用更大的 rollout 数(当前 50 次/任务/域在 1% 量级上分辨率不足);
6. **建真机子集** —— 哪怕只挑 10 个任务做 sim-to-real 对照,也足以让这套演示数据的产业价值从「未知」变为「可估」。

|---|---|---|
| **1 年内(至 2027)** | 🟡 **仿真评测层面:已落地。物理落地:不成立。** | ✅ **已落地**:106 任务 + 8,080 演示 + MIT 代码 + HF/ModelScope 双源数据**今天就能用于模型回归测试**。🔴 **物理落地不成立**:OOD 保持率 0.5%–12.9%、Memory 轴 ID 最高 33%、Long-Horizon OOD 4/7 模型 0/500 —— **即使 2027 年的策略有 2–3 倍提升,OOD 仍在 10%–40% 量级,远达不到产线要求** |
| **3 年内(至 2029)** | 🟡 **受控环境下的窄场景可能落地;通用双手灵巧家务不成立** | 🟢 **可能落地**:① 铰接机构操作(开微波炉/收银机/瓶盖 —— LD 轴 26 任务中 12 个是 K=1 单步,ID 已有 35–66% 成功率,这是**最接近可用的一段**);② 长时程但场景固定的工序(料箱取放、装配).🔴 **不成立**:Memory 轴(需真实状态记忆)、OOD 鲁棒性(需从 5% 抬到 90% 量级)、柔性/流体操作。⚠️ **关键前提:「落地」的定义必须是「固定 SKU + 固定工位 + 固定光照」,任何一项泛化都会重演 OOD 崩塌** |
| **5 年内(至 2031)** | 🟠 **有条件成立,条件是「基准被广泛采用」** | 🟢 **可期**:若 BiDex-100 这类「能力轴 + 匹配 ID/OOD + 进展分数」的范式被社区接受(它已经补齐了 §13.5 关心的「指标分离」),则**能力剖面会成为机器人策略的标准验收单**,采购方从「看 demo」转向「看 ID/OOD 双列 + 能力向量」。⚠️ **但通用家庭双手灵巧仍不乐观** —— 差距不在模型架构(7 个模型已覆盖 flow-matching/MoE/DiT/rectified-flow 全部主流 action expert 范式,最高 OOD 也只有 5.45%),**而在数据与接触物理保真度**。📌 **触发条件**:出现 (a) 柔性/流体的 MuJoCo 级高保真接触,或 (b) 一次可信的 sim-to-real 验证 —— **这两个条件本篇都没满足,且都不是三年内靠算力能解决的** |

## 横向对比:BiDex-100 vs HandsOn(同日同质工作)

📌 **两篇高度同质**(均为 2026-10 期间的双手/灵巧仿真基准),但**取向不同**。**本报告仅引用 HandsOn 论文自身的数字,未修改其任何文件。**

| 维度 | **BiDex-100**(本文,2610.25459) | **HandsOn**(2610.26765) |
|---|---|---|
| 机构 | 浙江大学 + **蚂蚁集团** | 清华大学 + 北邮 + NatureWill + 北大 |
| 任务数 | **106**(5 能力轴) | **66**(Core-50 + Transfer-16) |
| 演示 | **8,080 episodes / 6.25M frames / 94 GB** | **18,000 curated demos / 56 小时 / 3 视角** |
| 本体 | 2 种(dual Franka FR3 + Astribot S1),**均 22-DoF 灵巧手** | **5 臂 × 6 手** |
| 资产 | **266 可见资产 / 9 类,全刚体+铰接** | **约 200 资产,rigid + articulated + deformable** |
| 评分 | **进展分数 + strict success,latch/must-hold/latch-violation 三重门** | 分阶段诊断,暴露接触建立/动作协调/目标保持失败 |
| OOD | ✅ **匹配 ID/OOD 变体(6 族脚本化偏移)** | ✅ Transfer-16(资产/关系迁移、技能组合、**可变形迁移**) |
| 被测方法族 | **7 个 VLA**(flow-matching / MoE flow / DiT flow / rectified flow) | 扩散、VLA、world-action、**prompted VLM(GPT-6 + move_eef)** |
| 最优成绩 | **52.21% ID / 5.45% OOD** | **29.1% Core-50**(最优训练型多任务策略) |
| 零训练对照 | 无 | ✅ **GPT-6 + move_eef:Core-50 5.2% / Transfer-16 1.9%,660 trials** |
| 真机 | ❌ 无 | 🟡 **定性真机 rollout** |
| 开源 | ✅ **实测完整**(MIT + 212 YAML + 双源数据) | ✅ 仓库存在(<https://github.com/TsinghuaC3I/HandsOn>) |
| 统计严谨性 | 无置信区间 | ✅ **95% task-and-episode bootstrap 区间** |
| **最独特的贡献** | **进展分数 + 机器可检谓词 + 212 个可重放 ID/OOD 变体** | **跨本体 + 可变形 + 把 prompted VLM 纳入同一协议** |

**📌 本报告的对比判断**:

1. **两者的 ID/OOD 数字不可直接比较** —— 任务集、评分口径、域定义全不同(BiDex-100 的 OOD 是同任务偏移,Transfer-16 是换任务/换资产)。**任何「谁更强」的横向比较都是错的。**
2. **BiDex-100 的独特性在「可重放性」**:212 个 `__ood` YAML + 固定种子 + 匹配 reset 流程,意味着**第三方能精确复现每一个分数**;HandsOn 的 bootstrap 区间在**统计严谨性**上更强。**两者互补。**
3. **HandsOn 补上了 BiDex-100 缺的一块**:BiDex-100 测了 7 个 VLA 却**没有测「不用训练的 prompted VLM」**;HandsOn 测了 GPT-6 + move_eef(5.2% / 1.9% / 660 trials)。**这是一个重要对照:通用大模型在真灵巧控制上同样接近失效。**
4. **HandsOn 有柔性物体,BiDex-100 没有**;**BiDex-100 有跨本体 + 演示集,HandsOn 的本体更多但演示更短(56 h vs 69.4 h)**。
5. ⚠️ **对产业读者最实用的一条**:两篇**独立团队、独立机构、同一时间窗**测出的结论方向一致 —— **双手灵巧操控在当前 SOTA 上都处于「能跑、但离能用很远」的状态**(BiDex-100:最好 5.45% OOD;HandsOn:最好 29.1% Core-50、GPT-6 仅 5.2%)。**这种交叉印证比任何单篇结论都更可信。**

📌 **建议在本项目概念库中新增的三条线**(均来自本篇的独立发现,而非论文自述):

1. **「口径不对称」应成为本项目常设审查维度。** 本文 ID 域从录制的「机器人工作位姿」起步、OOD 域从默认复位位姿起步(**已在代码中定位**),而主文把 OOD 描述为「controlled visual and spatial changes」。**本项目 §12.3「变量控制」目前只查「对照是否同 seed / 同预算」,建议补一格:「两个被比较的条件,除目标变量外是否真的只差一个变量」** —— 姿态、初始化、任务集合的任一项不同,都会让「鲁棒性差距」读数失真。📌 这条与 §12.4(LIN-SLAM 的 ATE 表述被表内数字打折)是**同一种错误的不同形态:口径没说清,读者就会按字面理解。**
2. **「轴内变量混淆」是基准设计的独立失败模式。** 本文 Limited-Demos 轴同时改变了**演示条数(30 vs 100)** 与**任务难度(26 任务中 12 个是 K=1 单步)**,两个变量无法分离,于是「数据效率」结论不成立。📌 **建议固化为核查项:凡以「轴」为单位报告能力的基准,必须披露该轴内各任务的子任务数 / 阶段数分布,否则跨轴分数不可比。** 这与 §13.5「指标分离」互为镜像 —— 指标分离管「怎么算」,本条管「比什么」。
3. **「开源」必须按三档而非二档记录(对 §13.4 的修订建议)。** 本篇实测结论:仓库**不是 README 占位**,而是含 212 个可执行任务 YAML、7 个测试、双源数据集的**可用工程件**。📌 **建议把 §13.4 的三档口径细化为四档,并新增「已核验可用」一档**:(a) 链接 404;(b) 仅 README;(c) 代码在但数据/资产缺失;(d) **代码 + 数据 + 任务规范 + 测试齐备(本篇属此档)**。**并附实测方法:浅克隆后 `git ls-tree` 数任务 YAML 条数 —— 本篇为 106 base + 106 `__ood`,与论文「212 task-domain means」对上,这是一条 30 秒可完成的强验证。**
