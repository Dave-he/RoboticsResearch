## 核心问题

VLA 与 WAM 让**单台**机器人的操控与全身能力突飞猛进,但论文指出一个被忽略的边界:

> **单台机器人受限于其本体;而很多真实任务的能力,只能在协作中涌现。**

搬一件长物体穿过窄走廊,需要的是协同支撑、相对运动、转角协商和放置 —— **不是单个技能的聚合**。两台都能走、能转、能侧移的机器人,仍然必须决定**如何组合这些能力来搬运一个共享物体**。

论文把这个团队行为的形成称为 **co-becoming**:有效的协作,是通过**个体能力与共享物理状态之间关系的变化**来实现的。

**现有两类方案各有一半**:

| 路线 | 做法 | 缺什么 |
|---|---|---|
| 多机器人**规划** | 任务分解、分配、重规划 | **对「物理执行偏离预期时如何调整可执行的协作」支持极少** |
| **学习式**协作 | 联合策略 / 去中心化策略 | 策略需重训,不适配冻结的本体技能 |

**关键的物理事实**(论文的核心洞察):当机器人**被载荷物理耦合**时,一个个体的动作会同时改变**队友的支撑条件**和**后续联合动作的可行性**。

> **所以:一个有效的任务计划,并不保证当前的协作模式仍然可执行。**

**本文的可证伪命题**:

> **在个体运动技能固定的前提下,如何实例化并修订「可执行的团队协作代码」,使其适应共享物理任务的展开?**

**方法论上的一次根本转向**(这是本文与本项目已收录的多篇 code-policy 论文最重要的区别):

> **CoEvolve 修订的是「协作关系」,不是「机器人能力」。** 基础模型权重、电机策略权重 **全程冻结**。演化的对象是**任务计划、被实例化的协作策略、以及存储的经验**。

## 方法论与核心思路

### 整体架构:三角色 + 验证器闭环

```
┌──────────────────┬──────────────────────────────────────────────────┐
│  Task Orchestrator│  提交团队子任务 → 定义「要达成什么协作关系」      │
└────────┬─────────┴──────────────────────────────────────────────────┘
         │  z_t(子任务规格)
         ▼
┌──────────────────┬──────────────────────────────────────────────────┐
│   Policy Coder   │  多模态基础模型 → 生成「可执行协作代码」          │
│  (基础模型,冻结) │  · 运动原语 (motion primitives)                   │
│                  │  · 语义目标 (semantic objectives)                 │
│                  │  · 临时角色 (temporary robot roles)                │
│                  │  · 协调模式 (coordination modes)                   │
│                  │  · 有界执行参数 (bounded execution parameters)     │
└────────┬─────────┴──────────────────────────────────────────────────┘
         │  可执行策略对
         ▼
┌──────────────────┬──────────────────────────────────────────────────┐
│  物理执行 + 验证  │  Host 把配对的机器人策略当作「一个团队事务」校验    │
│  (MuJoCo)        │  每一次被派发的转移 → 接受 / 拒绝                │
└────────┬─────────┴──────────────────────────────────────────────────┘
         │  拒绝
         ▼
┌──────────────────┬──────────────────────────────────────────────────┐
│  结构化修订       │  从「最近一次被接受的 checkpoint」回滚            │
│  (Structured      │  修订对象分类:机动方式 / 角色关系 / 执行参数      │
│   Revision)      │  而非「无限制地重写策略」                        │
└────────┬─────────┴──────────────────────────────────────────────────┘
         │  被验证的经验
         ▼
┌──────────────────┬──────────────────────────────────────────────────┐
│  Verified        │  M^D:抽象协调记录(策略记录)→ 指导后续决策        │
│  Experience      │  M^A:被接受的代码范例 → 指导代码生成             │
└──────────────────┴──────────────────────────────────────────────────┘
```

**Algorithm 1(CoEvolve: Verifier Guided Coordination Evolution)的关键循环**:

1. 初始化计划 $P$、经验 $\mathcal{M}$、状态 $\bar{s} \leftarrow s_0$;
2. **保存 checkpoint** $C \leftarrow \textsc{SaveCheckpoint}(\bar{s})$;
3. 对 $t = 0, \ldots, B-1$:
   - 观测 $o_t$,取当前阶段 $q_t \leftarrow \textsc{ActivePhase}(P)$;
   - **检索策略记录** $r_t^D \leftarrow \textsc{RetrieveStrategy}(\mathcal{M}^D, q_t, \xi)$;
   - **编排** $z_t \leftarrow \textsc{Orchestrate}(g, o_t, P, r_t^D)$;
   - **检索代码范例** $r_t^A \leftarrow \textsc{RetrieveExemplar}(\mathcal{M}^A, z_t)$;
   - 生成并派发策略 → 物理执行 → 验证;
   - **接受** → 更新 $\bar{s}$、推进里程碑、存入经验;
   - **拒绝** → **回滚到 $C$**,触发**类型化修订**(typed revision),并把被拒转移计入物理预算(回滚**不退还**交互成本)。

### 关键创新 1:协作的「可执行表示」

论文不是从策略库里挑一个完整策略,而是**实例化**协作。实例化的载体是四类要素:

| 要素 | 作用 |
|---|---|
| **运动原语** | 可用的基础运动模式(推、绕、抬、跟…) |
| **语义目标** | 该原语要达成什么(而非具体关节量) |
| **临时角色** | 此刻谁做支撑、谁做搬运、谁做观察 —— **角色是临时的,不是固定的** |
| **有界执行参数** | 数量、幅度、持续时间等 —— **有界是为了让验证器能判定** |

> **「临时角色」是这篇论文最具特色的概念。** 在载荷转角这种受约束机动中,**支撑方与搬运方的角色会互换**;如果协作策略是固定角色库,转角就无法执行。论文在 §1 明确写到:「受约束的转弯需要**临时的支撑角色与搬运角色**」。

### 关键创新 2:类型化修订(Typed Revision)vs 反射式修订

论文 §4.4 用 **CaP-Agent0 的失败轨迹**说明了为什么「有反馈」不够:

> 在收到「需要不同的 yaw 修正量」的要求后,修复把两个值**都从 2.5 改成 2.0**,并**保留了被拒绝的那组关系**。

**类型化修订把变化拆成三个正交的轴**:机动方式(maneuver)、角色关系(role relation)、执行参数(execution parameters)。**这是从「重写一段代码」到「声明该改什么」的降维。**

### 关键创新 3:验证器只判定「局部可执行性」,而论文诚实地指出这不够

这是本文**最有价值的部分** —— 论文自己用两组实验证明了「验证通过 ≠ 任务能完成」:

**证据 A(§4.3,单个 GPT run 内部)**:在第 47 次事务达到第 4 个里程碑后,**剩余 33 次事务中有 31 次被接受**(含 27 次 setup 动作),**却再也没有任何一个里程碑被认证**。

> **即:EA(执行接受率)高到 94%,任务却卡死不动。** 这说明「执行有效」与「任务推进」是两个正交量。

**证据 B(§4.5,Layout 3)**:VP **58.3%**(三个布局中最高)、PAUC@160 **53.6%**(最高),**但 0/3 完成放置**。论文的解释:载荷是**有限接触支撑**而非刚性连接,**一次被接受的转移可能减少后续机动所需的支撑裕度**。

> **论文由此得出的判断(原话极有价值)**:
> > **"Checkpoint acceptance therefore certifies the executed transition, not the feasibility of the remaining task."**
> > **(checkpoint 的接受只认证了被执行的那个转移,并不认证剩余任务的可行性。)**

**因此论文把「支撑裕度」与「间隙裕度」明确列为「局部转移验证没有显式优化的约束」** —— 这是全篇最有价值的一个「已知盲区」声明。

## 核心公式提取

**验证进度(VP)** —— 最终可信 checkpoint 上已认证的里程碑占比:

$$
\mathrm{VP} = 100\,n^{-1}\sum_{r}\frac{q_r}{K_r}
$$

其中 $K_r$ 为场景定义的里程碑数,$q_r$ 为已认证数。

**执行接受率(EA)** —— 派发事务中被验证器接受的比例:

$$
\mathrm{EA} = 100\,n^{-1}\sum_{r}\frac{A_r}{T_r}
$$

> ⚠️ **两个重要的口径细节**:(a) **未解决的计费结果保留在分母中**,因此报出的是**确认下界**(论文用 $\ge$ 标记);(b) **EA 不统计派发前就失败的情况** —— 这正是为什么 Claude 的失败运行(在生成或修复阶段终止)完全不体现在 EA 上。

**进度 AUC(PAUC)** —— 衡量里程碑「何时」被首次获得:

$$
\mathrm{PAUC@}B = \frac{100}{n}\sum_{r=1}^{n}\frac{1}{K_r B}\sum_{k=1}^{K_r}\left[B - \min(\tau_{rk}, B)\right]
$$

其中 $\tau_{rk}$ 为里程碑 $k$ 首次被认证时累计的物理事务数,永不认证则 $\tau_{rk} = \infty$。

> **三个口径的设计意图非常清楚**:
> - **VP** = 最终**保留**了多少进度(终点状态)
> - **PAUC** = 进度是**多快**获得的(过程效率)
> - **EA** = 每次派发**有多少被接受**(局部执行合法性)
>
> **三者的分离正是本文的方法论内核。** 论文反复用这三者的不同排序来论证「单看任何一个都会误判」。

## 关键成果与贡献

### 主结果一:跨基础模型的可用性(Table 1,n = 5 / backbone)

| Backbone | 完整任务 SR@80 | VP (%) | EA (%) | PAUC@80 (%) |
|---|---:|---:|---:|---:|
| **GPT-5.4-mini** | **3/5(60.0%)** | **86.7** | 85.4 | 61.9 |
| **Gemini-3.5-Flash** | **3/5(60.0%)** | 76.7 | 66.7 | 60.2 |
| **Claude-Sonnet-4.6** | 2/5(40.0%) | 76.7 | **86.5** | **64.5** |

**三个 backbone 全部实现端到端成功** —— 这是「协作接口不绑定特定模型」的核心证据。

> ⚠️ **但这个表里藏着一个反例,论文自己点破了**:**Claude 的 EA 最高(86.5%)、PAUC 最高(64.5%),完成数却最少(2/5)。** Claude 的失败运行**终止在生成或修复阶段**,而 EA **不统计派发前失败**。**所以 EA 最高的模型反而完成得最少。**

### 主结果二:与基线对比(Table 2,GPT-5.4-mini,n = 5 / 条件)

| 方法 | 完整任务 SR@80 | VP (%) | EA (%) | PAUC@80 (%) |
|---|---:|---:|---:|---:|
| REMAC (Yuan+ 2026) | 0/5(0.0%) | 26.7 | 57.1 | 23.3 |
| COHERENT (Liu+ 2025a) | 0/5(0.0%) | 56.7 | **≥ 83.6** | 49.1 |
| CaP-Agent0 (Fu+ 2026) | 0/5(0.0%) | 33.3 | 66.7 | 29.5 |
| ASPIRE (Online) (Lu+ 2026) | 0/5(0.0%) | 40.0 | 74.9 | 35.6 |
| Flat Reflective Repair(变体) | 0/5(0.0%) | 43.3 | 73.2 | 36.3 |
| CoEvolve w/o Dynamic Experience(变体) | 0/5(0.0%) | 60.0 | 63.8 | 46.4 |
| **CoEvolve** | **3/5(60.0%)** | **86.7** | 85.4 | **61.9** |

**全部 4 个外部基线 + 2 个组件变体,完整任务成功率全部为 0/5。** CoEvolve 是唯一有完成记录的方法。

**两个变体的失败剖面差异**(比成功率本身更有信息量):

- **Flat Reflective Repair**:**4 次终止于载荷掉落上限**,1 次预算耗尽 —— 即「反复做错了方向的事」;
- **CoEvolve w/o Dynamic Experience**:**4 次生成/修复停滞 + 1 次预算耗尽** —— 即「不知道该往哪改」。

> **论文的归纳(原话)**:结构化修订定位**该改什么**,已验证经验提供**接下来该试什么的证据**;但论文**明确声明二者未被因果隔离**。

### 主结果三:跨布局泛化(Table 3,n = 3 / 布局)

| 布局 | 已验证放置 | VP (%) | EA (%) | PAUC@160 (%) |
|---|---:|---:|---:|---:|
| Layout 2 | 1/3(33.3%) | 41.7 | 71.4 | 30.3 |
| Layout 3 | **0/3(0.0%)** | **58.3** | 46.1 | **53.6** |
| Layout 4 | 1/3(33.3%) | 50.0 | 64.1 | 37.1 |

**Layout 3 是全篇最有诊断价值的一行**:进度指标全场最高,完成率却为零。**这直接证伪了「用进度指标选模型/选场景」的常见做法。**

> ⚠️ 论文自己标注了口径问题:Layout 4 的成功延续**使用了附录 B.5 描述的「精化的走廊验证条件」**,因此**不被当作纯几何匹配的复现实验**。**这个标注很诚实,但也意味着 Table 3 的三个布局并非同条件对比。**

### 主结果四:跨模型经验复用(Table 4,目标模型 = GPT-5.4-mini,n = 5 / 源)

| 源 → 目标 | 策略记录 / 动作范例 | 已验证放置 | VP (%) | EA (%) | PAUC@80 (%) |
|---|---|---:|---:|---:|---:|
| GPT → GPT | 17 / 14 | 1/5(20.0%) | 50.0 | 75.4 | 38.0 |
| Gemini → GPT | 16 / 8 | **2/5(40.0%)** | **76.7** | **80.3** | **55.8** |
| Claude → GPT | 4 / 8 | 0/5(0.0%) | 56.7 | **≥ 61.6** | 45.0 |

**最有意思的发现:经验库的规模不能解释复用效果。**

GPT 库有 17 条策略记录(最多),复用效果却最差(1/5);Gemini 库 16 条(次多),效果最好(2/5);Claude 库只有 4 条,最差(0/5)。论文的解释是**覆盖度与状态特定适用性**,而不是规模:

> GPT 虽然动作范例(14)比 Gemini(8)多,却**没有任何 pivot(转角)范例**,而 Gemini 和 Claude 都有。

> **这条结论对「经验库怎么攒」有直接工程含义:经验的价值来自「覆盖了哪些失败模式」,而不是「攒了多少条」。**

### 主结果五:被拒转移的机制差异(§4.4)

论文给了 **CoEvolve vs REMAC** 的执行级对照(Fig. 3):两者都到达了非平凡的转弯阶段,但**REMAC 先产生一个被拒的 pivot,再执行一个更小的被接受 pivot,随后终止于载荷掉落上限**;CoEvolve 则继续通过转角并完成。

> **论文的判词**:**「局部可执行性与验证器接受,不足以保证持续的任务推进:一个被接受的修正,仍可能把团队留在一个不支持剩余搬运序列的构型中。」**

### 附带结论:团队事务的原子性

论文定义「物理事务」为**一次联合派发的机器人命令**,并强调:控制器**保留各自的观测历史与执行线程**,因此**联合派发并不等于相同的物理响应**。回滚是**恢复被接受的模拟器状态**,而非物理可执行的恢复策略。

## 局限性与未来展望

### 论文自述的局限(§6,五条,逐条照录要点)

1. **墙钟成本高**:模型推理、物理执行、验证、恢复在一次运行中反复发生。
2. ⚠️ **回滚用的是「恢复模拟器状态」,不是「物理可执行的恢复策略」** —— **这直接限制了向真机迁移**。这是最致命的一条。
3. **冻结的电机接口只提供「有界的运动意图」,不是精确终点**:不等的机器人响应、停止后的残余运动、累积的编队漂移,会降低间隙并使共享载荷失稳。**载荷稳定性还依赖有限接触区域、摩擦与模拟器接触动力学 —— 本研究未对这些做系统随机化。**
4. **全部实验在仿真中**,使用**特权物理状态信息**与**给定的路线参考**。真机部署需要机载感知、更准确的运动与接触模型、安全的物理恢复,以及更广环境与硬件条件下的评估。
5. **评测队列小且异质**,限制了关于单个组件、场景泛化与经验迁移的强因果主张。

**Ethics Statement 里的一句关键限定(值得本项目单独引用)**:

> **"Although physical verification and recovery are used within the simulator, they should not be interpreted as safety guarantees for real-world deployment."**

### 本报告在阅读中发现的额外问题

1. ⚠️ **表格内部存在口径不一致,论文自己在 §4.2 承认**:"The full comparison condition reuses the GPT backbone runs, and **differences in runtime and continuation settings make the aggregate comparisons descriptive rather than matched causal estimates**." —— **即 Table 2 的基线对比不是严格配对实验。** 与 REMAC/COHERENT/CaP/ASPIRE 的对比,应读作「描述性」而非「因果性」。
2. ⚠️ **n = 5 的样本量对 3/5(60%) 这样的成功率不构成可靠估计。** 3/5 的 95% Wilson 置信区间约为 **23%–88%**。**「3 个 backbone 全部成功」在统计上远弱于其表面读感。**
3. ⚠️ **方法对比是「4 个基线全部 0/5」,这个对比本身有选择性风险。** 论文说明基线是「适配到同一协作运输任务与机器人接口」的,适配质量直接决定基线表现,而**论文未提供适配的充分细节**(附录 B.2 只记了一笔)。**「所有基线全 0」更可能反映「这些基线不是为这个任务设计的」,而不是「CoEvolve 显著更强」。**
4. ⚠️ **Table 3 的三个布局使用了不同的验证条件**(Layout 4 用了精化走廊验证),因此**布局间的横向比较不成立**。
5. ⚠️ **Table 4 缺少「空记忆」对照条件**,论文明确承认("the absence of a matched empty-memory condition prevent a causal transfer claim")。**因此「跨模型经验复用有效」本身未被因果证明。**
6. ⚠️ **SONIC 策略(Luo et al., 2026)是本文的底座,但论文未描述其能力边界**,而**「载荷 0.5 kg 自由支撑」是极简的耦合条件**。双机器人抬更大、形状不规则的物体时,「有限接触支撑」的脆弱性会被放大 —— 而这恰恰是论文自认的已知盲区。
7. ⚠️ **开源未兑现。** 承诺了 URL,实测 404。**虽然这是发表时点的问题(v2 于 10-19 更新),但它是本项目 §11.2 第三档,不能被引用为「开源」。**

### 一个值得本项目记住的方法论要点

> **本篇最重要的贡献不是「60% 成功率」,而是它用三个精心分离的指标,证明了「局部验证通过」与「任务可完成」是两个不同的东西。**
> 具体地:**EA 高 94% 而里程碑再也不前进;VP 最高(58.3%)而完成率为 0。**
> **这直接命中本项目此前反复遇到的一个痛点:BiGym 2.0 的「coding agent 全面胜过 demo-driven RL」也是靠分离指标得出的结论。** 可见 **2026 年 10 月,「指标如何分离」正在取代「指标能到多少」成为方法论的主战场。**
> **另一条更硬的结论是:checkpoint 接受只认证了被执行的那个转移,不认证剩余任务的可行性。** 这句话对所有做「执行反馈闭环」的系统(VLA 自改进、code policy、RL 后训练)都成立。

## 应用与行业映射(本项目强制要求)

### 1. 应用方向

- **物流 / 仓储**:多机器人协同搬运长件、货架搬运、包裹分拣的「转角协商」—— **本文的核心场景直接对应「狭窄巷道里两台机器人抬一根长梁」**。
- **工业装配 / 大件协同作业**:飞机/汽车总装中的大型部件多机器人抬装;风电叶片、桥梁段。
- **特种 / 救援**:废墟中的多机器人协同搬运(约束空间多);**海上平台的设备搬运**。
- **服务 / 酒店 / 医院**:双机器人协同配送大件(床、柜子),对「不撞人、不夹手」有直接需求。
- **⚠️ 明确不适合**:高动态、不可预测的开放环境(论文全在仿真,无真机、无机载感知)。

### 2. 行业玩家

| 公司 | 相关产品线 | 与本文的关系 |
|---|---|---|
| **Unitree** | **G1 人形**(本文双机器人平台) | **直接平台方**。G1 的开放性(可编程、可挂载)是多机器人协作研究的前提 —— **G1 已经是这类研究的默认实验台** |
| **宇树 / 智元 / 银河通用** | 人形 + 移动底盘队列 | 中国「人形 + 多机协同」的产能方。⚠️ **本文无真机结果,所以对量产厂商而言是「方向信号」而非「可用方案」** |
| **波士顿动力(Boston Dynamics)** | Atlas / Stretch(Stretch 专做箱件搬运) | Stretch 的单臂箱件搬运在产业上已落地;**多机协同的「长件搬运」正是 Stretch 这类产品的下一个延伸方向** |
| **Amazon Robotics** | Proteus / 移动机器人队列 | 仓储队列最成熟的产业玩家;**协同搬运的痛点在其仓库里真实存在** |

> **一个战略观察:宇树 G1 已成为多机器人协作研究的事实标准平台(本项目今日三篇里两篇都用了它)。** 这对宇树是重大利好 —— **G1 的「可编程 + 低价 + 现货」让它成为科研默认选项,而科研默认选项会变成产业默认选项。**

### 3. 替代方案

| 方案 | 成本量级 | 能力 | 与本文的对比 |
|---|---|---|---|
| **集中式多机器人规划器**(经典,含 LLM 规划) | 软件成本为主 | 能分解/分配/重规划 | **不擅长「物理耦合下的可执行性调整」** —— 这正是本文的靶心 |
| **联合策略 / 去中心化策略学习** | 需大规模多机 RL 训练 | 协调质量高 | **需重训本体技能**,与「本体冻结」的现实约束冲突 |
| **硬编码编队 + 阻抗控制** | 工程量大但确定性高 | 场景内稳定 | **无法应对未预见的几何**;场景一换就要重调参 |
| **遥操作 / 人工带队** | 最高(人力) | 100% 灵活 | **规模不可扩展**,成本随任务数线性增长 |
| **CoEvolve(本文)** | 基础模型 API 成本 + 已有运动技能 | 60% 完成率(仿真,n=5) | **唯一在本文对比中实现完成的**;但**全仿真、无真机** |

**成本量级**:CoEvolve 的边际成本 = **基础模型调用费 + 已有电机技能的复用**。相对于「重训多机联合策略」的数据成本,**接近于零**;相对于遥操作,**低 1–2 个数量级**。**这是它最诱人的地方,也是最需要真机验证的地方。**

### 4. 量产壁垒

| 环节 | 状态 | 卡点 |
|---|---|---|
| **算法** | ✅ 论文级完整 | 协调框架描述清楚,四个要素抽象合理 |
| **数据** | ✅ 无需真机数据 | 纯仿真 + 冻结技能。**这是最大的优势** |
| **算力 / 成本** | 🟡 可接受 | 基础模型 API 调用 × 80 事务预算 × 多条件;**但相比遥操作人力,便宜 1–2 个数量级** |
| **物理可靠性** | 🔴 **完全未验证** | 载荷 0.5 kg、自由支撑、仿真接触模型、**无系统接触随机化**。真机上双机器人抬 20 kg 长梁的接触耦合是另一个量级的问题 |
| **恢复机制** | 🔴 **结构性缺口** | **回滚 = 恢复模拟器状态,不是物理可执行的恢复策略**。真机没有「撤销」按钮。**这是从仿真到真机最硬的一道墙** |
| **感知** | 🔴 未涉及 | 全程使用**特权物理状态**与**给定路线参考**。真机需要机载感知 + 路线规划,本文完全没有这一层 |
| **安全** | 🔴 未涉及 | 论文 Ethics 明确声明模拟器内的「物理验证与恢复**不构成真机安全保证**」。双机器人抬载的失手会直接砸到人 |
| **开源** | 🔴 未兑现 | 404。**无法被第三方验证或改进** |

> **最硬的两个卡点:① 恢复机制不可物理执行;② 感知层完全缺失。** 两者叠加意味着 —— **这套系统离「可以让两台 G1 在仓库里抬货」还有整整一层工程。** 但也正因如此,**它离产业化的距离是「可测量」的,而不是「玄学」。**

### 5. 时间窗估计

- **1 年内(2026–2027)**:🔶 **学术原型可用,产业部署不可用**。最可能的落地:(a) **高校多机器人实验室的协同运输 benchmark**;(b) **仿真训练环境/数字孪生平台**的「多机器人协作策略生成」组件;(c) **Unitree 等厂商的开发者生态工具链**。**不会出现真机生产部署。**
- **3 年内(2028–2029)**:🟡 **窄场景可能落地**。触发条件:(a) **物理可执行的恢复策略**被解决(这是硬依赖);(b) 机载感知接口标准化(至少「给定路线参考」被替换为 SLAM 输出);(c) 一个 5 kg 级双机协同搬运的**真机基准**被建立。**最可能的第一个商业场景是「仓储中的双机抬运长件」** —— 那里既有真实痛点(长件搬运确实需要两台),也有可容忍的失败率(人工可以介入)。
- **5 年内(2030–2031)**:🟢 **「LLM 编排多机器人」很可能成为默认架构**。理由:多机器人系统的问题本质是**组合爆炸的协调问题**,而 2026 年的经验已经反复显示:**让 LLM 负责「协调层」、让 RL 负责「技能层」,是当前最优分工**。本文是这个分工的一个**具体可实现的实例**。**真正的竞争点会从「谁的方法更准」转向「谁的执行反馈闭环更鲁棒」** —— 而论文自己证明了鲁棒性(EA)与完成率(VP/PAUC)可以完全脱钩,这个脱钩会是未来 5 年的主要研究战场。

> **本项目的一条长期预判:2026 年 10 月的两篇(本文与已收录的 BiGym 2.0)共同显示 —— 「让基础模型编排、执行反馈闭环」已经是 2026 年的既定范式,不再是新意。** 接下来的差异化会来自**反馈信号的质量** —— 本文揭示的「局部验证 ≠ 全局可行」正是这个问题的第一个精确表述。**这个方向值得本项目长期设立专项追踪。**
